## 一、模型自动发现修复（patch10 系列）

### 1.1 商汤日日新生图模型拉取失败

**现象**：接口保存后自动发现的生图模型为 0，需要手填 `sensenova-u1.5-lite`。

**根因**（curl 实测）：`GET https://token.sensenova.cn/v1/models` 返回 200，列表里有
`sensenova-u1.5-lite` / `sensenova-u1-fast`，但上游是仿 OpenRouter 结构：能力声明在
`output_modalities: ["image"]` 字段，模型名不含 image 关键词、也没有 `type` 字段。
App 的 `parseModelList` 只认 关键词 / type / 模型名 三条规则，全部落空 → 兜底归入聊天模型。

**修复**：`parseModelList` 读取 `output_modalities`（smali 侧实现为：在 metadata 文本里把
`output_modalities":["image` 改写为既有关键词 `image_generation`，零分支改动）。

### 1.2 智谱 cogview/cogvideox 拉取失败

**根因**（curl 实测）：`GET https://open.bigmodel.cn/api/paas/v4/models` 只返回 10 个 GLM
聊天模型，CogView/CogVideoX **从不进模型列表**（上游设计如此），无自动发现途径。

**修复**：`normalizeProviderModels` 对 `bigmodel.cn` 并入内置清单（cogview-3-flash /
cogvideox-flash / cogvideox-3）。

**重要边界（patch10d 教训）**：同步机制是"只增不删"。内置清单若在每次同步都无条件注入，
用户删掉的模型会在保存时被加回。因此 **仅当该供应商对应列表为空（新条目）时注入**；
列表非空视为用户自管。剩余边界：把某类列表删到空再同步会被重新填充（与新建条目不可区分）。

### 1.3 smali 手写经验（本次新增踩坑）

| 坑 | 结论 |
|---|---|
| `invoke-direct ...-><init>()` 后跟 `move-result-object` | VerifyError `copyRes1 ... type=Conflict`：构造器返回 void，result 寄存器未赋值。正确写法：`invoke-direct/range {vX .. vY}` 后直接 `return-object vX` |
| 寄存器跨类型复用 + 多前驱合并点 | 出口标签尽量单前驱；`:skip_x` 类合并点两侧寄存器类型必须一致 |
| R8 裁剪后的 kotlin-stdlib | 新调用的 `CollectionsKt` 重载必须先 grep 确认存在于 APK（`plus(Iterable,Object)` / `listOf(Object)` / `distinct(Iterable)` 均在） |
| Compose 文本框 UI 自动化 | `input text`/Ctrl+A 焦点会跑偏；改配置一律 run-as 直改 prefs（先 force-stop） |
| `output_modalities":["image` 的转写 trick | 把上游字段改写成既有关键词，避免改动分支逻辑与寄存器布局 |

**验证**：商汤同步日志 `发现 8 个模型（聊天 6，生图 2，视频 0）`（修复前 聊天 8 生图 0）；
智谱 prefs 实写 `img=[cogview-3-flash] vid=[cogvideox-flash, cogvideox-3]`（此前为空）；
删除 cogvideox-3 后重新解析不再回滚。

## 二、商汤图生图协议 + 无水印（patch11/12）

### 2.1 根因与正确协议（以官方文档为准）

| 项 | 结论 |
|---|---|
| 编辑接口 | `POST /v1/images/edits`（**JSON**，同步；必须传输入图片，不能仅传 prompt） |
| images 元素 | **对象** `{"image_url": "公网URL 或 data:image/png;base64,xxx"}`；裸字符串数组 400 invalid arguments |
| 响应 | `response_format: "b64_json"`（url 模式链接 24h 过期） |
| 尺寸 | size 直传（1344x3136 竖版实测 200） |
| 水印 | **`"watermark": false` 是唯一有效写法**；`watermark_enabled` / `water_mark` 均无效；API 对未知字段宽松不报错，必须视觉判定 |
| 文生图 | 仍走 `/v1/images/generations`（edits 必须传图） |

排错过程中的弯路（避免重蹈）：`generations + images:[字符串]` 上游"有时跟随有时忽略"
（疑似多后端版本），一度误判为客户端 bug；后被同 body curl 复测 + prompt 矩阵证伪。
另：判定参考图是否被跟随时要先亲眼确认参考图内容——工作区里的 arrow.png/av1.png 实为 App 截图。

### 2.2 实现

`executeImage` 入口加 `baseUrl 含 sensenova` 分支 → `senseNovaImage()`：
- body = 原始请求 + model + `watermark:false`
- 有 `image_data` 时：转成 `images: [{"image_url": dataURL}]`，移除 image_data/image/image_url，
  端点切 `/images/edits`，加 `response_format:"b64_json"`
- 无 `image_data` 时：端点保持 `/images/generations`（原样透传 + 水印参数）

### 2.3 验证

- 经 App 本地网关（8800，Bearer token 见 `local_gateway_security.xml`）端到端：
  文生图/图生图均 200；图生图不再报 `invalid images...`
- 视觉判定：界面截图参考图 + "把图中箭头变成金色" → 同版式复刻、箭头变金、无水印；
  人像 + "把头发变蓝" → 发色变蓝、面部保留；两组出图均无水印角标
- 诊断日志：`logcat -s ImageRoute` 可见 `senseNovaImage images len=N`

## 四、追加（同日傍晚）：DeepSeek 发图无回复修复（patch13）

**现象**：中转 tab DeepSeek 发图片无回复。**根因**：装机 APK 的 assets 目录缺失
`sha3_wasm_bg.wasm`（smali 补丁流水线只打代码不打资产）→ ProxyService 启动时
PoW 初始化失败 → 所有 DeepSeek PoW 求解失败：图片上传异常被吞（DSRoute refFiles=0）、
completion 被静默断流。**修复**：把 wasm 拷入 `start-apk-work\decoded\assets\` 重打包。

**前置条件**：DeepSeek 会话需带 x-hif-leim 设备指纹（识图强校验）。普通文字聊天请求不带
该头，必须在 App 浏览器 tab 的 DeepSeek 页面发一条**带图**消息让页面发出指纹头，再点
"保存会话"。验证：中转发图 → DeepSeek 全文识图回复（Visual Description...）✓ 无水印 ✓。

**教训**：smali 补丁流水线改动不仅要迁代码，还要 diff 源码工程的 `assets/`（以及 res），
新文件不会凭空出现在 decoded 目录里。
