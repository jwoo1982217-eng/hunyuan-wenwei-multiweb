## 二、文心参考图注入（核心方案，chat/生图/视频通用）

### 2.1 为什么文心特殊（CDP 受控实验结论）

文心的文件 input（`.chat-input-function-file`）**只接受 isTrusted=true 的 change 事件**：

| 注入方式 | change 事件 | 页面反应 |
|---|---|---|
| JS DataTransfer + dispatchEvent | `isTrusted=false` | ❌ 完全忽略（files=1 但零网络）|
| CDP `DOM.setFileInputFiles` | `isTrusted=true` | ✅ 走上传链（PC 端验证）|
| **真实触摸 + 原生选择器** | `isTrusted=true` | ✅ **App 内唯一可行**（PC 的 CDP 方案 App 内不可用）|

### 2.2 最终可行路径（三通路统一）

```
真实触摸 "+"（.cs-input-plus-btn，MotionEvent 直发）
  → 菜单弹出（相机/相册/文件/打电话）
  → 真实触摸 "相册"（.chat-input-function-item 内的图标）
  → WebView 原生 onShowFileChooser 触发
  → NativeWebFileChooserBridge 喂文件（onReceiveValue 回调）
  → 页面自走上传链：/api/file/sts → bcebos 分片 PUT → /api/file/upload
  → 附件 chip 出现（.cs-input-file-container）
  → [兜底] 触摸路径失败 → JS DataTransfer 注入（此时页面会接受，因 change 已被原生桥激活）
```

### 2.3 坐标模型（血泪教训）

- `dispatchTouchEvent` 用 **WebView 局部坐标 = CSS × density**，**不能加 getLocationOnScreen 偏移**
  （加了会点到可视区外——本轮为此浪费数小时；adb 系统坐标 = CSS×dpr + WebView屏幕偏移，两者不同）
- 坐标必须**点击前一刻实时读取**（`getBoundingClientRect` 视口坐标随页面滚动漂移，实测漂移 100px+）
- 点击后校验菜单是否打开，失败重试（3 次）

### 2.4 心跳发送（chat 专用）

文心是 React 站点，合成 click 对发送按钮无效。方案：
- 后台线程等"附件 chip 就绪 + 输入框有文字"
- 心跳：读 `.cs-input-ds-send-btn` 中心 → **真实触摸** → 校验输入框清空（`textarea.value === ''`）
- 清空即成功；失败重试 12 拍（每拍 1.3s）

| 补丁 | 文件 | 内容 |

| patch29 | `CustomWebChatAutomation.smali` | chat 调用点前插文心分支（零寄存器：仅 `invoke-static`）|

**关键教训（防 VerifyError）**：
- 往 coroutine 状态机里插分支（if-eqz 等）会导致 ART 验证器拒绝整个方法（`register type Conflict`）——本轮踩了两次
- **正确做法：把逻辑全部内聚到 Java 侧，smali 只插无分支的 `invoke-static`（零新寄存器）**
- `move-object` 的 12x 格式只支持 v0-v15，从 v16+ 取值必须用 `move-object/from16`
- Java 方法参数类型必须与 smali 调用签名**完全一致**（本轮 `Object` vs `CustomWebProviderConfig` 导致 NoSuchMethodError → 500）

## 四、构建注意事项（踩坑合集）

1. **d8 必须传全部 class**（含 `$1`/`$2` 等匿名内部类），漏传 → `NoClassDefFoundError`
2. **javac 用 stub 目录**：`-classpath android.jar;tmp_javaclass/stubs`，stub 只给 javac 看，**不要**把 stub 的 class 传进 d8
3. **覆盖 decoded 树前先删旧 WenxinAttachmentUploader*.smali**（类结构变了会残留）
4. smali 文件禁用 PowerShell 读写（BOM/CRLF），一律 Python
5. apktool 打包前确认 smali 无语法错（`Invalid register` / `Could not smali file` 会在 b 阶段才报）

## 七、本轮教训增量

1. **用户手动操作是金标准**：文心的"原生选择器路径"就是用户手点出来的；CDP 实验只用于确认原理，最终方案必须是 App 内可执行的
2. **"UI 没变就别查结构"**（用户原话）：chat 和生图/视频的输入区是同一个组件，注入方式完全通用——不要重复做页面结构调研
3. **VerifyError 排查**：报 `register vN has type Conflict` 就是插入了破坏类型流的分支——改用"Java 内聚 + 零寄存器 invoke"模式
4. **心跳模式复用**：patch20/21（文心视频心跳发送）→ 本轮 chat 心跳发送 → 一脉相承，模式是"`__go` 封装 + tick 重跑 + 成功信号即停"
5. **无参静态调用是 smali 补丁的终极安全区**：`invoke-static {}` 不碰任何寄存器，能最大程度规避验证器问题

# 09-21 追加：上游风控封禁的排查方法论与经验归纳（重点沉淀）

> 背景：09-20～09-21 连续踩了两个上游通道风控（WorkBuddy CLI chat 403/11140、
> 豆包桌面协议 710022005），累计 60+ 次受控实验，把这类问题的排查路径固化成方法论。
> **结论先行：两个案例都不是代码/配置问题，是上游对「非官方客户端通道」的账号级/端点级风控。**

## 一、两个案例的现象与最终定性

| 案例 | 现象 | 最终定性 |
|---|---|---|
| WorkBuddy CLI chat | `POST /v2/chat/completions` 全模型 403 `code=11140 request illegal`，displayMsg 误导性提示「内容未通过安全审核」 | **账号级 chat 端点风控**：同账号 models API 200 正常、网页版（Cookie）正常、换 token/重授权无效 |
| 豆包桌面协议 | `POST /chat/completion` 返 200 + SSE 头后立刻 `STREAM_ERROR 710022005 系统错误` 断流（183B），App 读空流抛 EOFException | **上游对桌面客户端协议的时段性风控**：早上同款请求成功（8.3KB 完整流），当天高频测试后全拒；网页版正常 |

共同信号：**「早上通、下午封」+ 当天有高强度自动化测试**——频控触发的时间窗特征明显。

## 二、排查方法论（按成本排序，每层独立可复现）

1. **同域对照定位范围**：用同域其他 API（如 WorkBuddy `/v2/enterprises/personal/models`）
   区分「账号全封」还是「单端点封」。models 200 + chat 403 ⇒ 端点级，账号无事。
2. **时间线还原**：找「最后一次成功」的时间点和当时请求特征。成功→失败的转折点
   附近往往就是触发事件（密集测试、批量 refresh、协议变更）。
3. **请求维度逐个排除**（每维一两次实验，别叠变量）：
   token 新旧（refresh 后的 vs 老的）→ uid（JWT sub 比对）→ headers（把官方客户端
   smali 契约完整复现，一套套试）→ body（官方独有字段）→ IP（宿主出口 vs 设备出口）
   → 消息内容 → 模型名。
4. **通道对照**：同账号的网页版/Cookie 通道是否正常。网页正常 + API 拒 ⇒ 通道级风控，
   账号健康，别去折腾登录态。
5. **账号 vs token**：「换 token 无效」不能证明账号健康也不能证明账号被封——要看新 token
   的 JWT sub 是否还是同一个人。同 sub 全拒 = 绑账号。
6. **官方 App 对照**（终极实验）：设备上装官方桥接壳/官方客户端，实测同端点。
   它通 = 客户端指纹（TLS/连接特征）检测；它也不通 = 账号/策略级。

## 三、关键教训（血泪）

1. **`request illegal` / `内容未通过安全审核` / `系统错误` 都是误导性文案**——真实含义
   是「请求被风控拒」，别去改消息内容、别怀疑模型名，直接查通道。
2. **「Bearer-only 即可」这类结论有保质期**：09-15 实测成立的假设，09-20 上游加校验后
   全部失效。协议类结论必须带复测日期。
3. **密集自动化测试会触发上游频控**：当天 60+ 次请求把两个通道相继打封。测试脚本必须
   加间隔（≥30s）、失败即停，别在排错时疯狂重试。
4. **复现官方客户端契约要完整**：本次从 bridge 壳 smali 挖出两套契约（Z1 15 头 /
   T1 20+ 头 + body 字段 `outbound_client_name`/`passthrough_ip`），虽最终仍被拒，
   但这是排除「协议缺字段」假设的唯一办法。
5. **App 的「错误透传」是现成诊断通道**：中转 tab 直接显示上游 403 原文，
   比曲线抓包快得多（本次豆包 EOFException 就是靠 UI 报错 + 直连复现定位的）。
6. **写 prefs 前先 force-stop App**：App 内存态会在后台 persist 覆盖手改文件
   （本次删供应商条目先踩后改）；另外 `adb push` 不要包在 `adb shell` 里（静默失败）。

# 09-21 追加三：WorkBuddy 网页自动化——卡点终态与剩余路线（接追加二）

## 一、本轮新确认的事实（全部有实证）

1. **注入已通**：`execCommand('insertText')` 注入会被编辑器 state 接受（re-render 后
   文字保留即为证）；原生 `adb input text` 也能进 state（hello 曾出现，后被 race 清掉）。
2. **发送全路败（网络层铁证）**：JS click / CDP 完整鼠标序列 / CDP rawKeyEvent Enter /
   设备级 `input keyevent KEYCODE_ENTER` / CSS fixed 搬运+系统 tap——**全部无法触发
   chat 请求**（CDP Network 监听只有 conversations 列表刷新，零聊天请求）。
   期间见过两次「输入框清空」均为假象（本地 re-render，无网络请求）。
3. **布局溢出（页面根因）**：页面布局宽 ≈518 CSS，但 WebView 视口只有 360 CSS
   （dpr=3，物理 1080×1242）——**发送钮位于布局 x=474，在横向溢出区，用户视觉上
   也被裁掉/缩放**。这不是简单的坐标问题，是 App WebView 宽度/UA 让页面选了错误
   布局断点。发送钮 fixed 搬运也无效（祖先 transform 包含块陷阱）。
4. Enter 确实是发送键（main.js：`"send-message" defaultMac/Win:"Enter"`），
   genie.js 有 handleSendPrompt——但程序化按键到不了那个 handler。

## 二、剩余路线（按推荐排序，下轮直接照做）

1. **页面内 fetch 直发（最推荐）**：CDP evaluate 里跑同源 fetch，cookie 自动带、
   header 用页面同款（X-User-Id 等从页面请求抄），完全绕过按钮。需先从 main.js 扒
   `/console/as/` 聊天端点的 URL/body/header 格式（acct.js 已有大量 /console/as/
   端点清单可参考；genie.js 有 handleSendPrompt 上下文）。SSE 流用 fetch reader 读。
2. **修 App WebView viewport**：查 MainActivity.kt 的 WebSettings（useWideViewPort /
   loadWithOverviewMode / UA），让页面按 360 宽正确自适应，发送钮回到视口内——
   这可能同时修复真实用户的手动发送（布局溢出对真人同样存在，需验证）。
3. **真实 MotionEvent**：App 内 dispatchTouchEvent（CDP 的鼠标对 React 无效，
   但 App 原生 MotionEvent 是 isTrusted=true）——坐标需先解决布局溢出。
